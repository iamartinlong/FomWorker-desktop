# 技能创建助手

把「怎么建一个技能」一次讲全：**位置、目录结构、形状、路径、生效时机、验证方法**。
按本技能做，不必再去翻仓库文档。

## 1. 三个技能根与优先级

所有根都在 `$DSH_HOME` 下。**同名技能按 rank 决胜，数值越小越先胜出**：

| 类型 | source | rank | 位置 | 谁写 |
|---|---|---|---|---|
| 随包（bundled） | `bundled` | 600 | `apps/fom-client/plugins/office-skills/assets/<name>/SKILL.md` | 开发者，随安装包发布 |
| **用户自建（managed）** | `custom` | **500** | `$DSH_HOME/office/skills/<slug>/SKILL.md` | 用户 / agent ← **本技能的主战场** |
| 平台下发（platform） | `platform` | 550 | `$DSH_HOME/office/platform-skills/<slug>/SKILL.md` | 平台目录同步 |

⇒ **用户自建盖过随包与平台下发**（本地优先）。要改一个随包技能的行为，
在受管根建一个同名的即可，不用去改安装包里的文件。

**解析 `$DSH_HOME`（动态取，不要写死路径）**：环境变量 `DSH_HOME` 优先，
否则 `~/.dsh`。FomWorker 装机版被数据隔离钉在 `%APPDATA%\FomWorker\dsh-home`。
拿不准就先跑一条命令确认（如 `echo $env:DSH_HOME` / `echo $DSH_HOME`），
或直接问运行时，**别把某台机器的绝对路径写进技能正文**。

## 2. 技能的目录结构：一个技能不止一个文件

```
<root>/<slug>/
├── SKILL.md          ← 必需：frontmatter + 给模型的指令正文
├── references/       ← 可选：按需加载的参考文档（细节、规范、长表格）
├── scripts/          ← 可选：确定性 / 重复性劳动的固化的可执行代码
└── assets/           ← 可选：产出里要用的文件（模板、图标、字体）
```

**为什么值得用**：模型看到技能时，会同时被告知「这个技能的基目录是 `<上面这个路径>`，
正文里提到的相对路径都对着它解析，**按需加载**」。所以：

- 正文保持精炼，**细节挪进 `references/`**，正文只留一句「细节见 `references/xxx.md`」；
- 参考文档超过 300 行就在它自己开头加一个目录；
- 一个技能要支撑**多套流程**时按变体分文件（`references/aws.md` / `references/gcp.md`），
  模型只会去读它需要的那一份；
- **每次调用都在重写同一个辅助脚本**，是「该把它挪进 `scripts/`」的强信号——
  写一次，以后每次调用都复用，省掉反复造轮子。

正文没有硬性长度上限（内核原样装载），但长正文每次都占上下文，**精炼是对模型的体贴**。

## 3. SKILL.md 的形状与 description 写法

```
---
name: 展示名（可中文）
description: 什么时候该用本技能——菜单与模型都靠它决定要不要调用
---

# 正文标题

（给模型的指令：工作流、产出形状、纪律）
```

**description 是触发的唯一主机制**，值得多花心思：

- **「何时该用」全部写在这里，不要写进正文**——正文只在技能被触发后才读得到，
  那时已经晚了；description 是模型动手前唯一能看到的东西。
- **写得「主动」一点**。模型倾向于**少触发**技能（很多它能自己应付的就不调用），
  所以别只写「是什么」，要把典型说法、近义说法、以及「用户没明说但其实需要」的场景列出来。

  **不好**：`汇总一周工作数据生成周报。`
  **好**：`周报汇总 —— 汇总一周工作数据（多维表格记录 / 日历日程 / 工作区文件）生成结构化周报，
  可发布为飞书云文档。当用户要求「写周报 / 汇总本周工作」或提供了多维表格、日历数据时使用。`

- **`/` 菜单的主标签只能是 kebab-case 标识**，所以**中文展示名要放进 description**，
  否则菜单里只看到一串英文 slug。
- **受管技能的标识就是 slug（目录名）**；frontmatter 的 `name` 只是 description 的兜底，
  菜单显示的是 `description`，没有它才退到 `name`、再退到 slug。
- slug 作目录名，规则 `^[a-z0-9][a-z0-9._-]*$`：小写字母数字开头，只允许 `.` `_` `-`。
  **大写、空格、中文一律非法**（会在输入边界被拒）。
- frontmatter 用 `---` 包夹、`name`/`description` 各占一行；正文紧随其后。
  写完后 frontmatter 会被剥掉，模型只看到正文。

⚠️ **随包技能是例外**：它的 description 写在 `office-skills/index.ts` 的 `SKILLS` 数组里，
**不读 frontmatter**。改 `assets/<name>/SKILL.md` 里的 description 对界面零影响——
只有受管 / 平台下发两个根读 frontmatter。（有一条单测钉着两边逐字相等，改任一侧另一侧会红。）

## 4. 动手前先问清

写之前先把这四个问题过一遍，缺答案就别动手——尤其是第 2 个：

1. **这个技能要让模型能做什么？**（一句话）
2. **什么时候该触发？**（用户会怎么说？这正是 description 的原料）
3. **产出是什么形状？**（固定模板？自由文本？要不要给个样例）
4. **需不需要测试用例？** 产出可客观验证的（文件转换、数据提取、固定流程）值得配；
   主观性强的（文风、设计）通常不必。按技能类型给建议，让用户定。

**当前对话里可能已经有答案**：用户说「把刚才这套流程固化成技能」时，
先从对话历史里挖——用过的工具、步骤顺序、用户纠正过什么、输入输出长什么样，
再让用户补缺的口。**不要重复问用户已经给过的信息。**

## 5. 三条创建路径

| 路径 | 怎么做 | 生效时机 | 前提 |
|---|---|---|---|
| **A. agent 的 write 工具**（推荐） | 直接写 `$DSH_HOME/office/skills/<slug>/SKILL.md` | **同一会话内**即时生效 | 无 |
| B. 控制台写端点 | `POST /api/office/console/action`，body `{"action":"skill.create","payload":{"slug":"…","name":"…","description":"…","body":"…"}}` | 即时 | 需登录；owner/admin/member 均可，**不需审批** |
| C. 控制台 UI | 「专家·技能·连接器」页 → 技能 → 新建 | 即时 | 同上 |

路径 A 为什么即时：受管根挂了目录监听 + 接了内核 `fs/observed`，
写入会触发一次刷新，把技能收集缓存清掉。

**正文里该写什么**：工作流步骤、产出形状、**纪律**。技能只是**给模型的指令**——
它**不引入任何新工具、也不放宽任何闸**；需要写飞书这类对外动作，照旧弹审批卡，
不要试图绕过。

## 6. 写完怎么验证

1. **不要重启应用**——重启能掩盖问题（进程重建会清缓存，旧 bug 就是这样被藏住的）。
2. **新开一个会话**，看技能列表里有没有刚建的那条；或直接问 agent「你现在有哪些技能？」。
3. **再用 2-3 个真实用户会说的提示跑一遍**，看产出对不对。
   写提示时往**难处**写：口语化、带错别字、缺关键信息、和别的技能沾边——
   「格式化这份数据」这种一句话不算，那种你自己一步就能做完的更不算。
4. **顺带记两条近失样本**（关键词沾边、但其实不该用这个技能的），
   它们最能说明 description 写得准不准。

看不到 ⇒ 按顺序查：slug 是否非法、文件是否真在 `<root>/<slug>/SKILL.md`、
frontmatter 是否被 `---` 正确包夹、`description` 是否缺失。

## 7. 删除 / 导出 / 导入

- **删**：`skill.remove`（payload `{slug}`），或直接删掉整个 `<root>/<slug>/` 目录。
- **导出**：`skill.export`（payload `{slug}`）⇒ 得到 portable 技能包
  （`kind:'fom-skill'` + `version` + 解析时未知键静默忽略），可分享。
- **导入**：`skill.import`（payload `{bundle}`）⇒ 同 `slug` 已存在会 409。

三条都走路径 B 那个端点，都需要登录。

## 8. 纪律

- **先问清再写**：slug、展示名、触发场景（description）三项缺一项就别动手
  （见 §4 四问）——特别是 description，它决定模型什么时候调用这个技能。
- **技能内容不该让用户意外**：不做恶意、不做伪装成别的东西、不做帮人绕过授权的技能。
  这条与产品的审批模型是同一套价值观——对外动作照样走审批，技能不是绕口。
- **不写死机器路径**：技能正文里出现 `$DSH_HOME` 要教怎么解析，不是抄某台机器的绝对路径。
- **技能不是工具**：不要指望通过技能「增加能力」；能力来自工具与插件，技能只是编排指令。
- **多解释「为什么」，少堆「必须」**：模型不笨，给它理由它能举一反三；
  只有安全与正确性红线才值得用绝对化的措辞。
- **正文保持可读**：一段工作流一件事；细节进 `references/`（见 §2），
  别把 SKILL.md 撑成一本手册。
